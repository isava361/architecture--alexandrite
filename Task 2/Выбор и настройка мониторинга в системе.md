Мотивация

Почему мониторинг нужен прямо сейчас:
1. Рост нагрузки (каждый месяц +100 заказов) уже выявил латентные ограничения: жалобы B2C/B2B, потеря контрактов. Без наблюдаемости мы «слепы» и чинить можем только пост‑фактум.
2. Критический путь заказа проходит через тяжёлую вычислительную стадию (расчёт цены), очереди и несколько БД. Любая задержка без метрик превращается в «не получили заказ».
3. Единичные инстансы повышают риск деградации/простоя. Мониторинг даст ранние сигналы по утилизации/насыщению и позволит обосновать масштабирование/репликацию.
4. Доверие клиентов и операторов: SLI/SLO по времени этапов, прозрачные отчёты и алерты снизят эскалации, позволят управлять ожиданиями.
5. Скорость релизов: видимость производственных регрессий (latency/ошибки/очереди) сократит катастрофические «ручные» проверки, даст уверенность при выкладках.

Что это даст компании:
1. Сокращение просрочек и быстрое выявление причин (узкое место видно сразу: очередь, БД, конкретный клиент API, конкретный эндпоинт).
2. Стабилизацию B2B‑канала (квоты/лимиты/алерты по клиентам), снижение оттока партнёров.

Выбор подхода к мониторингу

RED — для всех HTTP/GraphQL API: Shop API, CRM API, MES API, внешнее B2B API. Быстро показывает деградацию сервисов.
USE — для инфраструктуры и брокера/БД: RabbitMQ, PostgreSQL. Даёт ранние сигналы ресурсов.
Четыре золотых сигнала — для фронтендов (Vue/React) и внешних интеграций. Полезно для пользовательского опыта и внешних зависимостей.


Метрики:
1. HTTP:
  Response time (latency) for shop API
    Зачем: RED‑latency по эндпоинтам магазина.
    Ярлыки: service="shop-api", endpoint, method, status_code, channel (b2c/b2b), customer_region
  Number of errors
    Зачем: RED‑errors по 5xx/4xx
    Ярлыки: service, endpoint, status_code, error_type.
  Kb tranferred (received) for shop API/Kb provided (sent) for shop API
    Зачем: нагрузка/скорость загрузки 3D‑файлов, выявление сетевых проблем
    Ярлыки: service, content_type, file_size_bucket (e.g. 0-10MB, 10-50MB, 50-200MB, 200MB+)
  Request Duration
    Зачем: доступность и задержки хранилища, влияние на критический путь.
    Ярлыки: operation (PUT/GET/HEAD), bucket, status_code/error
2. CRM
  Response time (latency) for CRM
    Зачем: RED-latency для CRM
    Ярлыки: service="crm-api", endpoint, method, status_code
  Number of errors
    Зачем: RED‑errors по 5xx/4xx
    Ярлыки: service, endpoint, status_code, error_type.
  Request Duration
    Зачем: доступность и задержки хранилища, влияние на критический путь.
    Ярлыки: operation (PUT/GET/HEAD), bucket, status_code/error
3. MES
  Response time (latency) for MES
    Зачем: RED-latency для MES
    Ярлыки: service="mes-api", endpoint, method, status_code
  Number of errors
    Зачем: RED‑errors по 5xx/4xx
    Ярлыки: service, endpoint, status_code, error_type.
  Kb tranferred (received) for shop API/Kb provided (sent) for shop API
    Зачем: нагрузка/скорость загрузки 3D‑файлов, выявление сетевых проблем
    Ярлыки: service, content_type, file_size_bucket (e.g. 0-10MB, 10-50MB, 50-200MB, 200MB+)
  Request Duration
    Зачем: доступность и задержки хранилища, влияние на критический путь.
    Ярлыки: operation (PUT/GET/HEAD), bucket, status_code/error
4. RabbitMQ
  Number of dead-letter-exchange letters in RabbitMQ
    Зачем: индикатор отказов маршрутизации/обработки; рост = потеря заказов.
    Ярлыки: queue, reason (reject/expired), routing_key.
  Number of messages in flight (unacked/prefetched) in RabbitMQ
    Зачем: «застревание» у потребителей, признак back-pressure.
    Ярлыки: vhost, queue, consumer.
  Queue length / ready messages (новая метрика)
    Зачем: базовый уровень очереди; длительный рост — отставание обработки.
    Ярлыки: queue.
  Consumer errors / requeue rate (новая метрика)
    Зачем: кодовые ошибки хендлеров.
    Ярлыки: queue, exception_class.
5. Базы данных
  Memory Utilisation for shop db / MES db instance
    Зачем: буфер-кеш и риск свопа.
    Ярлыки: db_role (primary), engine (PostgreSQL).
  Number of connections for shop db / MES db
    Зачем: пул соединений, риск исчерпания лимитов.
    Ярлыки: app.
  Size of shop db / MES db instance
    Зачем: рост, планирование, вакуум/автосборка
    Ярлыки: db_instance.


План Действий:

Этап 0. Базовая платформа
Создать инстанс time‑series хранилища: Prometheus, persistent диски в Yandex Cloud.
Развернуть Grafana. Настроить каналы оповещений (Slack/Telegram/Email), шаблоны и маршрутизацию.
Подготовить OpenTelemetry Collector с экспортом метрик/трейсов/логов в выбранные бэкенды.

Этап 1. Инфраструктурные метрики (USE)
Подключить postgres_exporter к Shop DB и MES DB; выдать минимальные роли чтения статистики; включить pg_stat_statements.
Подключить rabbitmq_exporter; включить management plugin; создать read‑only пользователя для экспорта.
Создать дашборды Grafana: «PostgreSQL (общий/по базам)», «RabbitMQ (очереди и потребители)».

Этап 2. Метрики приложений (RED)
Включить метрики приложений
Реализовать бизнес‑метрики
Стандартизировать ярлыки: service, env, endpoint.
Добавить аннотации релизов (release notes) в Grafana/Prometheus для корреляции событий.
