Мотивация

Проблемы:
1. Медленная "первая страница" MES с новыми заказами
2. Долгая обработка/пересчёт цены - при ретраях B2B клиенты многократно вызывают расчёт
3. Большой объём повторяющихся чтений бьёт в PostgreSQL и замедляет весь контур

Цели кеширования:
1. Ускорить чтение горячих данных (список самых новых заказов для операторов, карточка заказа, справочники)
2. Снизить нагрузку на базу и MES API
3. Избежать повторного тяжёлого расчёта цены при идентичных входных данных

Что кешируем в первую очередь:
1. Лента новых заказов - первая страница MES, top N и страницы 1–3
2. Карточка заказа (агрегированная информация по статусам и истории)
3. Результаты расчёта цены
4. Справочники (материалы, доп. опции) — для UI и сервера

Предлагаемое решение

Типы кеширования:
1. Серверное кеширование (Redis Cluster) — основной слой для MES/CRM/Shop API. Причины - контроль консистентности, атомарные инвалидации, низкая задержка, поддержка структур данных (sorted set/sets) для ленты.

Паттерны:
1. Лента новых заказов (MES dashboard) - Write-Through. При создании/переходе заказа в "видимые" статусы — сначала пишем в БД (транзакция), затем публикуем событие order.status.changed и обновляем Redis - добавляем/обновляем запись. Для страниц (page=1..3) кешируем подготовленные списки ключами для пикового трафика.
2. Карточка заказа - Cache-Aside. При выполнении запроса заказов сначала вызываем Redis. При miss читаем из БД, кладём в кеш.
3. Результаты расчёта цены - Write-Through. После завершения расчёта — сохраняем в БД и одновременно в кеш. При изменении тарифов/алгоритма — меняем priceVersion, что мгновенно инвалидирует старые ключи по namespace.
4. Справочники: Refresh-Ahead. Карточка и справочники читаются часто, меняются редко, следовательно можно использоват Refresh-Ahead

Чем хуже альтернативы:
1. Лента новых заказов и Результаты расчета цены - Часто меняются данные, создаются новые Cache-Aside и Refresh Ahead не подойдут. Проще, чем инвалидировать по куче условий. Трудно предсказать, какие именно заказы появятся
2. Карточка заказа - редко меняется, дешевле использовать Cache-Aside
3. Справочники - Крайне редко меняется, можно инвалидировать ассинхронно


Стратегия инвалидации:
|По ключу/событиям|Временная|Другие|
|Точная и быстрая консистентность после изменения статуса, контролируемые инвалидации ленты|Простая, защищает от забытой инвалидации|При версионировании придётся прокидывать текущую версию в все места, формирующие ключ|
|Требует дисциплины событий|Возможны устаревшие данные на 3–60 сек|Не применим например для ленты - непредсказуемость набора данных|
