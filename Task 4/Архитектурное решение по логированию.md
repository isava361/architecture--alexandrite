Что и где логировать (привязка к C4 и статусам заказа)

Логи собираем из всех мест, где заказ меняет состояние либо покидает границы сервиса (отмечено зеленым на схеме)
1. Сбор логов с систем: Shop API (Spring Boot), CRM API (Spring Boot), MES API (C#).
2. Фронтенды (Vue/React)
3. RabbitMQ
4. БД PostgreSQL
5. S3-совместимое хранилище 3D-файлов

Список ключевых логов уровня INFO (по бизнес-сценариям):
1. Статусы заказа - order.id, from, to, sources, actor (seller/operator/system), reason (если есть)
2. Создание/обновление заказа - order.created, order.updated
3. B2B-API b2b.order.request.received, b2b.order.created, b2b.order.duplicate_ignored
4. Очереди/MES-CRM - mq.publish , mq.consume.start/finish, mq.dead_lettered
5. Расчёт цены (MES) - price.calc.started/finished
6. Действия оператора - operator.pick_order, operator.stage.progress
7. Отправка/закрытие - order.shipped, order.closed
8. Файлы - file.upload.started/finished file.download.failed, reason
9. Инфраструктура - db.slow_query, db.lock_detected, rabbitmq.consumer.down/up

Другие уровни логирования:
DEBUG — только в dev/release
WARN — ожидали успех, но с ретраями
ERROR — операция не выполнилась
FATAL — критический сбой процесса/инстанса
AUDIT — вход в админку, смена ролей, выгрузки данных


Мотивация

Зачем логирование:
1. Сократить время расследований - можно выполнить мгновенный поиск по order.id и цепочке событий
2. Уменьшить нагрузку на поддержку
3. Повысить доверие B2B - получаем доказуемость причин просрочек по api.client_id
4. Ускорить релизы - быстрый откат по росту ERROR

Метрики, на которые влияет логирование:
1. Уменьшится MTTR инцидентов "пропал заказ"/"завис статус"
2. Уменьшится доля тикетов с "не установлена причина"
3. Снизится ERROR-rate по сервисам и доля DLQ сообщений

Приоритет внедрения (первый этап):
1. MES бэкенд (расчёт, присвоение оператору) — главный узкий участок.
2. RabbitMQ (publish/consume/DLQ) — место "потери" заказов.
3. CRM API (создание заказа из очереди, CLOSED) — окончание пути и B2B интеграция.
4. В последнюю очередь - Shop API (загрузка файлов/SUBMITTED), фронтенды, PostgreSQL (slow query/locks), S3-access.

Предлагаемое решение (технологии, безопасность, хранение)

Стек и поток:
1. Приложения пишут структурированные JSON логи
2. Включаем OpenTelemetry logs (или Promtail tailing файла/STDOUT)
3. OpenTelemetry Collector — единая точка приёма логов
4. Хранилище логов: Grafana Loki (занимает мало места на диске, легкая интеграция с графаной для трейсинга)
5. Долгосрочный архив: S3

Новые компоненты на диаграмме:

ССЫЛКА

Политика безопасности логов:
1. Минимизация - никаких ПДн/платёжных данных в логах. User ID — только в виде хеша
2. Маскирование в Collector
3. Шифрование - TLS в транзите, шифрование хранилища
4. Доступы: Grafana RBAC — роли "Поддержка", "Разработчик", "Админ". Доступ к prod-логам только по заявке. Вести аудит обращений.
5. Юрисдикция: хранение в пределах Yandex Cloud региона, контроль экспорта.

Политика хранения:
1. В Loki — 14 дней для приложений, 30 дней для AUDIT/безопасности.
2. Архив в S3: 90–180 дней, с компрессией


Необходимые мероприятия для превращения системы сбора логов в систему анализа логов

Алертинг (Grafana Alerting, LogQL):
1. Алерты на ERROR-rate больше базового порога за 5–10 мин.
2. Stuck orders - нет логов перехода статуса SUBMITTED в PRICE_CALCULATED > X минут
3. DLQ всплеск - mq.dead_lettered > 0
5. Медленные запросы - db.slow_query > N/мин
6. Ошибки фронтенда - рост frontend.error

Поиск аномалий/злоупотреблений:
1. Всплеск b2b.order.request.received — детект DDoS/скриптов.
2. Резкое увеличение file.upload.failed - проблемы сети/S3.
3. operator.pick_order резкое падение — зависла "первая страница"
