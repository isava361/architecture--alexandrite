Где заказ «ломается» и что покрывать трейcингом

Критический путь заказа пересекает 3 приложения, очереди, БД и тяжёлую асинхронную стадию (расчёт цены). Любая потеря/разрыв контекста = «заказ пропал». Покрываем всё, где меняется статус или передаются сообщения/файлы:
1. Онлайн-магазин
2. MES
3. CRM
4. RabbitMQ
5. Взаимодействие MES↔CRM.
6. S3-хранилище 3D-файлов
7. Базы данных (Shop DB, MES DB)

Типовые «поломки», куда целимся трейсингом:
1. Застревание между SUBMITTED и PRICE_CALCULATED
2. Потеря/дубликат сообщений при создании B2B-заказов
3. Медленная «первая страница» MES
4. Неидемпотентные ретраи калькуляции/доставки сообщений
5. «Дыры» статусов (нет события о переходе/записался, но не дошёл).

2) Какие данные писать (минимальный/полезный набор)

1. Корреляция и идентификация
2. Версии сервисов: service.version, env (dev/release/prod).
3. Статусы и этапы
4. Ошибки/таймауты

Мотивация

  1. Слепые зоны между системами = потерянные/зависшие заказы. Сквозной трейс показывает, где именно оборвался путь: HTTP-эндпоинт, очередь, воркер, БД.
  2. B2B-доверие и удержание: быстрое доказательство причин (по клиенту/ключу API), SLO по этапам, алерты — меньше эскалаций и штрафов.
  3. Скорость релизов: регрессии видны сразу (рост длительности спанов и доля ошибок), меньше ручных блокеров релиза.
  4. Экономика: нормирование узких мест (очереди/калькуляция) вместо массового масштабирования.

  Метрики (технические/бизнес) с улучшением от трейсинга:

  1. 95-й перцентиль времени SUBMITTED-PRICE_CALCULATED и APPROVED - MANUFACTURING_STARTED.
  2. Уменьшится Доля заказов "без перехода статуса более X часов"
  3. Уменьшится доля B2B-заказов с повторной доставкой/дубликатами сообщений
  4. Уменьшится количество инцидентов "пропажа заказа" (по журналу трейсинга до конкретного шага).

Предлагаемое решение

1. Технологии

OpenTelemetry: Java, .NET (MES), JS-RUM  (Vue/React) — прокидываем W3C Trace Context (traceparent, tracestate) через все HTTP-вызовы и RabbitMQ headers для асинхронных запросов.

OTel Collector как единая точка приёма OTLP (traces/logs/metrics), маршрутизация/фильтрация/сэмплинг.

Хранилище трейсинга: Jaeger + Grafana для просмотра и дешбордов.


2. Ключевые моменты реализации

Асинхронное общение и очереди:
— при публикации сообщения создаём span "enqueue" и кладём traceparent в headers. При обработке сообщения — span "process" с Parent=FromHeaders
— измеряем задержку очереди: consume.start - enqueue.end
— чётко логируем messaging.message_id и retry.count

Долгая калькуляция цены:
— отдельный span "price_calculation" с периодическими event ("started", "checkpoint N", "finished"), чтобы не держать гигантский открытый span часами.

Frontend - Backend:
— JS-SDK отправляет трейс и прокидывает traceparent в XHR/fetch
— CORS/headers настроить так, чтобы бэкенды принимали и продолжали контекст
— Для "первой страницы MES" включаем инструментацию SQL с маскировкой и атрибутами db.operation, db.table, что покажет кто вызывает задержку


Где смотреть:
— В Grafana поиск по order.id="..." покажет полную ленту событий по заказу на одном экране.
— Для поддержки можно добавить в CRM прямую кнопку "Открыть в Grafana по order.id".

Обновленная диаграмма C4:
ССЫЛКА

Компромисы

1. Cтарые участки, где нельзя добавить SDK останутся "чёрными ящиками"
2. Сверхдлинные процессы (занимающие дни) будут иметь громоздкие трейсы
3. Высокая стоимость хранения при 100% сэмплинге
4. Сторонние B2B-клиенты не всегда передают traceparent

Безопасность и доступ
1. SSO/RBAC в Grafana - доступ только сотрудникам с ролями "Поддержка", "Разработчик", "Администратор", раздельные права на просмотры
2. Безопасность передачи данных: OTLP mTLS между сервисами и Collector. Частная сеть для Tempo/Grafana. Доступ извне — через VPN
3. Санитизация ПДн на уровне Collector (процессор редактирования атрибутов), запрет логировать персональные данные в attributes
4. Секреты (ключи B2B, токены) не пишем в трейсы
5. Настроить аудит: логи входа в Grafana, API-доступа Tempo, изменения дашбордов
